# Экипировка, использование и ресурсы

## Модель предмета

Один физический предмет/стопка — одна запись `inventory[]` с уникальным `uid`.
Руки **не содержат копий** предметов. Связи — по UID, а не по имени.

```json
{
  "uid": "bow-1", "name": "Длинный лук", "type": "weapon", "qty": 1,
  "handedness": "two", "hand_slot": "both", "equipped": true,
  "consume": {
    "enabled": true, "resource": "quantity", "trigger": "attack",
    "amount": 1, "target_uid": "", "ammo_tag": "arrow"
  },
  "actions": [
    {"name": "Атака", "kind": "attack", "roll": "d20+@atk_dex"},
    {"name": "Урон", "kind": "damage", "roll": "d8+@dex"}
  ]
}
```

- `handedness`: `none`, `one`, `two`, `versatile`.
- `hand_slot`: `main`, `off`, `both`, `null`. Для экипированного носимого предмета
  без рук используется `equipped: true`, `hand_slot: null`.
- Двуручное оружие вытесняет предметы из обеих рук в рюкзак. Смена слота не
  создаёт и не удаляет записи инвентаря. Универсальное можно взять одной/двумя руками.
- Чтобы экипировать предмет из стопки, сначала отделите одну штуку. При разделении
  количество сохраняется, отделённая часть получает новый UID, без экипировки/настройки.
- У действия может быть `grip: one | two | ""`: варианты урона универсального оружия
  исключают друг друга, в связке «Всё» не бросаются оба. Хват проверяет и сервер.
- Старые флажки `equipped` мигрируют в свободные слоты; конфликтующие предметы
  остаются в рюкзаке, не теряются. Повторяющиеся UID отвергаются, а не размножаются.

## Расход

Настройки доступны в редакторе каждого предмета (и шаблона справочника):

- включить/выключить автоматику;
- количество (`quantity`) или заряды (`charges`);
- сам предмет (`target_uid: self`), конкретный UID инвентаря или автоматический
  поиск по `ammo_tag` (`arrow`, `bolt`, `bullet` либо своя метка);
- сколько и когда: за каждую выбранную атаку (`attack`) либо один раз за использование/связку (`use`).

У луков/арбалетов из справочника по умолчанию включён расход соответствующих
боеприпасов, у расходников — своей единицы. Настройки конкретного экземпляра
не меняют шаблон и другие экземпляры. Отключённый расход не включается заново
при перезагрузке или миграции.

При стрельбе расход идёт **за атаку**, независимо от попадания/промаха/крита.
«Атака + урон» расходует одну стрелу; отдельный бросок урона — не расходует.
Если в связке несколько разных действий атаки — расход за каждое.
Автопоиск может добрать ресурс из нескольких стопок по порядку инвентаря;
конкретная привязка не заменяется другой стопкой молча. Удалённый/переданный
источник требует переназначения. При нуле количество остаётся нулём, запись
сохраняет UID и связи; предмет не возрождается через `qty || 1`.

Проверка хвата, количества, всех формул и списание выполняются на сервере.
Недостаток ресурса или неверная формула отменяет **всю** операцию, без броска в чат
и частичного списания. Успех возвращает детализацию `spent`, которую показывает
общий DiceEngine. Повтор такого результата идёт через использование предмета,
а не через бесплатный повтор формулы. Карточка предмета в чате открывает лист
владельца; кнопка теста в редакторе явно тестирует только формулу, без расхода.

## Стартовое снаряжение из мастера создания

Мастер создания (`docs/character-builder.md`) наполняет `sheet.inventory` теми же
записями, что и лист персонажа: `uid`, `qty`, `type`, `handedness`, `hand_slot`,
`worn_slot`, `equipped`, `consume`, `actions`, `desc`, `source`. Никаких
параллельных форматов — каждый предмет проходит `Equipment.normalize`, поэтому
сразу работают стопки, разделение, расход и слоты.

- Предмет из справочника становится шаблоном (`template_id`) и получает `actions`
  из `mechanics.item_defaults`; при отсутствии шаблона создаётся предмет по
  названию с `type: gear`.
- Количество из текста класса/предыстории (`×10`, `(10)`, «два») хранится в `qty`
  одной стопки: 10 факелов — одна запись с `qty: 10`, а не 10 записей.
- Наборы, разложенные на содержимое, дают родительскую строку (`pack: true`,
  `contents: N`) и дочерние предметы с полем `parent` и `qty`, умноженным на
  количество наборов. Выключенный выключатель «Раскладывать наборы» оставляет
  набор одной строкой.
- «Надеть доспех, щит и основное оружие сразу» расставляет `hand_slot`/`worn_slot`
  по общим правилам: доспех — на тело, щит — во вторую руку, одноручное — в
  основную, двуручное — только когда обе руки свободны.
- Золото из варианта «(Б) … зм» и из поля «Дополнительное золото» пишется в
  `sheet.currency.gp`. Блок `sheet.creation.equipment` хранит снимок выбора
  (`gold` и список предметов) как историю создания.

Стопку из мастера нельзя взять в руки целиком: как и на листе, сначала нужно
отделить одну штуку (кнопка разделения). Это осознанное поведение, а не ошибка.

## Слоты по правилам и настройка

На вкладке «Основное» рядом с руками стоит панель «Слоты по правилам»: она показывает, что надето в каждый слот
(основная и вторая рука, обе руки, доспех, голова, шея, плащ, перчатки, пояс, обувь и два кольца) и какие правила
соблюдены или нарушены — один доспех, не больше одного щита, двуручное оружие занимает обе руки, по одному кольцу
на руку, настройка только у предметов с требованием настройки и не больше трёх одновременно. Нарушения показаны
предупреждением с причиной, корректная раскладка — строкой «настройка N/3».

Правила настройки обеспечивает `Equipment.migrate`: настроенным считается не больше трёх предметов с
`attunement: true`, у остальных флаг `attuned` снимается при нормализации (в том числе у предметов, которым
настройка не нужна), а предметы с настройкой без `attuned` не дают бонус к КД и помечаются предупреждением.
Проверки живут в `Equipment.slotsAudit(sheet)` и покрыты `tests/equipment.test.cjs`.

## Производный КД

Опция «КД от доспеха, щита и Ловкости» пересчитывает значение с нуля: без брони
`10 + Ловкость`, либо надетый доспех и его ограничение Ловкости, плюс один щит в руке.
Ничего не прибавляется повторно при перетаскивании шаблона. Ручное изменение КД
отключает автоматический расчёт. Для особой защиты классов/магических формул
используйте ручной КД. У существующих листов опция не включается принудительно.
Это не полный валидатор боевых правил: стили боя, ограничения второй руки,
владения, бонусные действия, возврат метательного оружия и восстановление стрел
после боя не автоматизированы.

## Согласованность и API

Добавлены миграции БД: `characters.revision` и `character_operations`.

`GET /api/characters/:id` возвращает `revision` и `sheet._revision`.
Любой `PATCH` с полным `sheet` должен передать прочитанную `_revision`.
Устаревшие и отсутствующие версии получают **409**: другое окно не сможет
вернуть списанные ресурсы старым автосохранением. Пустой PATCH остаётся проверкой
прав и не увеличивает версию. Встроенные клиенты передают версию с листом;
сторонним клиентам нужно обновить протокол. Старые открытые вкладки обновите.

```json
POST /api/characters/:id/inventory
{
  "request_id": "уникальный UUID, до 64 символов",
  "op": "use", "item_uid": "bow-1", "actions": [0, 1], "mode": "adv"
}
```

Также поддерживаются `equip` (`slot: main/off/both/worn/backpack`),
`split` (`qty`), `drop` (`scene_id`, `x`, `y`, `size`) и `pickup` (`scene_id`, `loot_id`).
Один request_id повторно возвращает сохранённый результат, не расходует ресурс
и не бросает кубики повторно. При неизвестном исходе сети лист предлагает повтор
**того же** запроса; автоматического переброса нет. Записи идемпотентности живут
до удаления персонажа (удаляются каскадно), очистка по TTL пока не реализована.

Расход, результат броска, запись чата и ключ операции фиксируются в одной
транзакции; WebSocket-события отправляются после commit. При конфликте версий
изменения откатываются. Скрытое использование на столе доступно GM.

Передача между персонажами обновляет оба листа одной транзакцией с проверками
версий; порядок блокировок определяется ID. `/transfer` принимает `request_id`
для безопасного повтора частичной передачи. Встроенный API-клиент добавляет его.
Переданный предмет теряет слот/настройку, но его настройки расхода сохраняются;
привязка к ресурсу исходного персонажа становится недоступной и требует выбора.

Выкладывание физического предмета одновременно удаляет его из инвентаря и создаёт
`managed_loot` на сцене. Подбор одновременно удаляет лут и добавляет предмет
получателю: два игрока не смогут подобрать один токен. Позднее перемещение не
воссоздаёт уже удалённый токен. Такой лут нельзя клонировать кнопкой дублирования
или вместе с копией сцены. Создание нового предмета из шаблона — отдельная,
намеренная операция. Владельцы по-прежнему могут вручную редактировать свой лист:
эти механизмы защищают от гонок/повторов, а не от намеренного редактирования правил.

## Проверки

- `node --test tests/*.test.cjs` — правила интерфейса и регрессии, включая разбор
  стартового снаряжения (`tests/character-builder-equipment.test.cjs`).
- `node tests/equipment.browser.cjs` — настоящий интерфейс листа с API-фикстурой:
  две руки, единый экземпляр, двойное нажатие, расход, отключение, узкий экран.
- `cargo test inventory::tests` — серверные инварианты, расход, откат, хват, стопки.
- `scripts/smoke.sh` запускает `tests/inventory-api.py` на реальном сервере:
  идемпотентность, устаревшие версии, права, передача и конкурентный подбор лута.
