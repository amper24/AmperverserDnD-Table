# Нодовая система v3

Цель: маленькие ортогональные блоки, условия у каждого блока, результаты действий,
доступные другим действиям, и понятная палитра без легаси. Обратной совместимости нет.

## Принципы

1. **Один блок — один глагол.** Блок либо вычисляет значение, либо меняет лист/предмет,
   либо управляет потоком. Составные узлы (adjust+condition+passive) сливаются в один
   `action.field` с параметром `kind`, как уже сделано для `rule.value/list/class`.
2. **Условие у каждого блока.** У всех блоков есть входы `enabled` (статическое условие:
   редакция/уровень/подкласс/выбор) и `condition` (динамическое bool-значение). Если
   условие ложно, блок пропускается, а поток идёт дальше по exec-выходу. Ветвление
   (`flow.if`) остаётся только для случаев, где нужны разные продолжения цепочки.
3. **Результаты принадлежат листу.** Выполнение действия пишет итог в лист:
   `sheet.action_results = { last: {...}, by_program: { "<program_id>": {...} } }`.
   Узел `data.result` читает последнее действие или конкретную программу; `data.sheet`
   читает поле листа. Так одно действие может «посмотреть», что дало другое действие на
   этом же листе, и использовать это в условиях и формулах.
4. **Поток статический, значения — в рантайме.** План блоков (`to_v1_with_context`)
   остаётся: поток и порядок блоков известны при компиляции. Для динамического условия
   в план кладётся `condition_src` — id узла-источника; сервер вычисляет его значение в
   рантайме той же функцией, что и при компиляции (`mechanics_graph::node_value`), но с
   контекстом `{"runtime": {"sheet": <лист>, "results": <action_results>, "vars": <переменные>}}`.
   `flow.if` по-прежнему выбирает ветвь статически (при неизвестном значении остаются обе ветви).
   Значение `action.setvar` с проводом на `value` тоже вычисляется в рантайме (`value_src`).
5. **Палитра закрытая.** Незнакомый тип узла — ошибка; алиасов нет.

## Палитра v3

Порядок категорий в меню — рабочий процесс: **Начало → Действия → Данные → Условия → Правила → Группы**.
У каждого типа есть короткое описание одной строкой (подсказка в меню и на карточке).
Заголовки карточек действий, данных, условий и правил единообразны: `Действие · …`, `Данные · …`,
`Условие · …`, `Правило · …`; у настраиваемых узлов после названия идёт выбранный вид
(`Действие · Бросок · Атака`). Короткие имена остаются у `action.program` («Начало действия»),
`flow.if` («Если»), `flow.end` («Конец») и узлов групп.

Отдельных узлов изменения состояния, показателя и параметра при создании больше нет — их
заменяет один `action.field` с параметром `kind`; расход предметных ресурсов — `action.spend`,
ячейка заклинания — отдельный `action.slot`; сравнение чисел переехало в `data.compare`.
`data.boolean` остаётся как константа.

### action.roll

Бросок с видом `kind` (roll / attack / damage / heal / temp_hp), кубиками, DC и
режимом преимущества. Лечение и временные хиты применяются сразу и всегда к владельцу
листа; урон — это бросок, результат которого применяет ДМ (или `action.field` по его
решению). Поля `target`/`apply` из старых блоков палитра не создаёт, а `apply`
исполнение не читает.

`upcast` = `{ count, sides }` — сколько костей добавляется к урону или лечению за
каждый круг ячейки выше базового. Сервер дописывает `+(extra*count)d<sides>` к формуле
только у блоков damage/heal; у атаки и свободного броска параметр не действует.

### action.field

Изменение листа или состояния: `kind` = status / value / formula. `status` — имя
состояния в параметре `condition` и операция add/remove; операция `concentration`
оставляет `condition` пустым — сервер сам подставляет «Концентрация: <имя заклинания>»
и заменяет прежнюю запись. `value` — поле листа `field` и целое `amount`; `formula` —
пассивный параметр при создании (`field`, `value`, например формула защиты без доспехов).
Урон, лечение и временные хиты — это броски `action.roll`, а не `action.field`.

### action.spend

Расход ресурса: `resource` = quantity / charges / uses, источник `source` =
self / item / tag, `amount` и момент `trigger` = use / attack.

### action.slot

Расход ячейки заклинания. `level` = 0 — круг выбран при касте (сервер берёт его из
операции и контекста каста), 1–9 — фиксированный круг. `amount` — сколько ячеек
списать. В план блока исполнения узел компилируется в `consume` с `resource: "slot"`
и `slot_level`. При ритуале (круг каста 0) блок пропускается: ячейка не тратится.

### Руки и слоты

У листа две обычные руки — `main` и `off`. Поле `sheet.extra_hands` (целое 0–4, по умолчанию 0)
добавляет дополнительные руки: слоты `extra1`..`extra4`. Слот `extraN` существует, только пока
`N ≤ extra_hands`; при уменьшении поля предметы с исчезнувших слотов возвращаются в рюкзак с тем
же количеством. Это делает `normalize` на сервере и его зеркало `Equipment.migrate` на клиенте:
несуществующий слот — не ошибка листа, а повод снять предмет.

- `both` — двуручный хват: занимает `main` и `off` сразу. Двуручное оружие (`handedness: two`)
  в дополнительную руку не берётся: `equip` отвечает ошибкой, а панель рук не предлагает его
  в списке дополнительной руки.
- Одноручное и универсальное оружие в дополнительной руке держат одной рукой; универсальное
  может занять `both`, если свободны обе обычные руки.
- Предмет без слота при нормализации получает первую свободную руку: `main`, затем `off`,
  затем `extra1`..`extraN`.
- Экипировка в дополнительную руку атомарна, как и в обычную: она вытесняет предмет из этого
  слота, а не создаёт копию; предметы из стопки сначала отделяют.

Узел `action.hands` меняет `extra_hands` блоком `hands`: `add` и `remove` — на `count`
дополнительных рук, `set` — общее число рук (`extra_hands = count − 2`, то есть 2 — обычные
`main`+`off`, 3 — одна дополнительная). `count` — целое 1–6, а `extra_hands` не выходит из 0–4;
`set` со значением 1 считается двумя руками. Если рук стало меньше, предметы с исчезнувших
слотов снимаются, а эффект действия перечисляет их в `removed`. Панель рук показывает слоты
`extra1`..`extraN` с подписями «Доп. рука N» и строку «Рук: N», когда дополнительных рук больше нуля.

### data.result / data.sheet / data.cast

`data.result` — выход `value: number`, входов нет. Параметры:
`source` = `last` (последнее выполненное действие) или `program_id` программы этого
графа; `field` = `total` | `hit` | `applied` | `spent`. `hit` отдаётся числом 0/1.
Значение берётся из `sheet.action_results` (см. ниже); без состояния выполнения
(редактор, предпросмотр) — `0`.

`data.sheet` — выход `value: number`, входов нет. Параметр `field` — непустой путь по
ключевым полям листа из `[a-z0-9_.]` (`hp.current`, `level`, `abilities.str`).
Отсутствующее или нечисловое поле — `0`; без листа (предпросмотр) — тоже `0`.

`data.cast` — выход `value: number`, входов нет. Параметр `field` = `level` (круг
выбранной ячейки) | `base` (базовый круг заклинания) | `extra` (круги выше базового).
Читается из контекста каста; без каста (редактор, предпросмотр) — `0`.
Все три узла дают `number`: они подключаются к `data.compare`/`data.math` и к числовым
входам правил (`amount`). К входу `dice` их подключить нельзя — там тип `dice`.

### Условия

Условия — это маленькие узлы с одним выходом `value: bool` и без входов. Два из них
считаются по снимку листа при компиляции (`condition.context` — редакция, уровень,
подкласс, выбор; `condition.hit` — попадание предыдущей атаки), остальные четыре читают
**лист исполнения** и поэтому работают только в рантайме — через вход `condition` блока
(`condition_src`), а не через `flow.if`:

| Узел | Что читает | Параметры |
|---|---|---|
| `condition.status` | `sheet.conditions` (список строк) | `name` — название состояния (до 120 символов, пустое — ошибка), `mode` = `present` / `absent` |
| `condition.item` | `sheet.inventory` (список предметов) | `name` — название предмета (до 120 символов, пустое — ошибка), `mode` = `owned` (есть в снаряжении) / `equipped` (флаг `equipped`) |
| `condition.hp` | `sheet.hp.current` и `sheet.hp.max` | `op` = `lt` / `le` / `gt` / `ge`, `value` (при `percent: true` — 0–100, иначе 0–1000000), `percent` = true/false |
| `condition.slot` | `sheet.spells.slots[level]` (max − used) | `level` = 1–9, `op` = `gte` / `lt`, `value` = 0–20 |

- Сравнение состояния и предмета — **по строке**: «Отравленный» и «отравленный» — разные
  значения. `condition.status` смотрит в `sheet.conditions`, `condition.item` — в
  `sheet.inventory` по полю `name`.
- `condition.hp` при `percent: true` считает `current * 100 / max`; если максимум равен 0,
  процент считается нулевым. Без листа (`hp` нет) результат — `false`.
- `condition.slot` берёт остаток `max − used`. Если круг совпадает с кругом пула Договора
  (`sheet.spells.pact_slots.level` и `pact_slots.max > 0`), остаток берётся из `pact_slots`;
  отсутствующий круг — остаток 0.
- Без контекста исполнения (редактор, предпросмотр) все четыре узла дают `false`: блок с
  таким условием в предпросмотре скрыт (в рантайме его включает сервер). Это то же
  ограничение, что у `data.result`/`data.sheet` (см. «Результаты выполнения»).
- Поэтому провод от условия листа допустим **только ко входу `condition` блока действия**
  (единственное место, где появляется `condition_src`); провод к `enabled` или к `flow.if`
  отклоняется с подсказкой — эти входы считаются статически и молча выключили бы блок.
  `condition.hit` по-прежнему подключается только ко входу `condition` узла «Если».

### Результаты выполнения

После успешного действия сервер пишет в лист:

```json
{
  "action_results": {
    "last": { "total": 12, "hit": true, "applied": 0, "spent": 1, "rolls": 2, "at": 1760000000 },
    "by_program": {
      "<program_id>": { "total": 12, "hit": true, "applied": 0, "spent": 1, "rolls": 2, "at": 1760000000 }
    }
  }
}
```

- `total` — итог последнего броска действия (0, если бросков не было);
- `hit` — попадание атаки: `true`/`false`, `null` без броска атаки (в `data.result` — 0/1);
- `applied` — сумма эффектов `heal`/`temp_hp`/`damage`; урон приходит броском и на лист
  не применяется (его применяет ДМ), поэтому на практике это лечение и временные хиты;
- `spent` — сумма израсходованных ресурсов;
- `rolls` — число бросков действия; `at` — unix-секунды выполнения.
- `last` перезаписывается каждым успешным действием, `by_program` хранит итог каждой
  программы и не теряет ранее записанные программы.
- Ошибка на любом шаге по-прежнему откатывает лист целиком: результаты пишутся только
  после выполнения всей цепочки. Ответ `execute` содержит этот же объект в поле `results`.

Условие блока считается в рантайме: если ко входу `condition` подведён провод, в блок
плана попадает `condition_src`, и сервер вычисляет узел-источник по текущему листу и
результатам. `false` или `0` пропускает блок, поток идёт дальше по `exec`; неизвестный
узел — ошибка выполнения (лист не меняется). В редакторе предпросмотр остаётся
статическим: `data.result`/`data.sheet` без состояния дают `0`, поэтому блок с таким
условием в предпросмотре может быть скрыт.

`flow.if` остаётся статическим: его `condition` вычисляется при компиляции без контекста
выполнения. Поэтому `data.result`, `data.sheet` и `data.cast` в условии `flow.if` дают `0`,
и ветка «да» отбрасывается ещё до исполнения. Для условий, зависящих от листа и результатов,
используйте вход `condition` самого блока: он компилируется в `condition_src` и считается
в рантайме.

## Переменные и ссылки

Четыре узла дают небольшую «память» внутри действия: `action.setvar` пишет число,
`data.var` читает его обратно, `data.ref` подставляет значение другого узла, а
`data.mathfun` считает функцию одного числа или диапазона. Переменные — всегда числа;
текст, списки и объекты в `sheet.vars` не поддерживаются.

### Области переменной

`action.setvar` и `data.var` имеют параметр `scope`:

| `scope` | Где живёт значение | Кто видит |
|---|---|---|
| `action` (по умолчанию) | карта выполнения `runtime.vars` | блоки этого действия после `setvar`; после выполнения значение исчезает |
| `sheet` | `sheet.vars` на листе персонажа | это и последующие действия; значение хранится в записи листа |

- `sheet.vars` — объект «имя → число». При старте выполнения его числовые значения
  копируются в `runtime.vars`; всё, что записано с `scope: "sheet"`, сразу попадает и в
  `sheet.vars`, и в `runtime.vars`. Переменные действия в лист не сохраняются.
- Имя — 1–32 символа `[a-z0-9_]`; область — только `action` или `sheet`. Эти же проверки
  повторяет сервер при сохранении и при исполнении.
- Значение `action.setvar` берётся с входа `value`: если провод есть, сервер считает
  узел-источник в рантайме (в план попадает `value_src`) — так работают `data.var`,
  `data.result`, `data.sheet` и цепочки `mathfun`/`ref`; без провода значение равно `0`
  (или числу из параметра `value`, если блок пришёл из старого плана).
- Нечисловое значение провода — ошибка выполнения; лист при этом не меняется (как и при
  любой другой ошибке цепочки).

`data.var` — выход `value: number`, входов нет. Читает `runtime.vars[name]`; для
`scope: "sheet"` дополнительно смотрит `sheet.vars` (в рантайме обе карты синхронны).
Неизвестное имя, нечисловое значение и предпросмотр без состояния выполнения дают `0`.
Поэтому `data.var` в условии `flow.if` статически равен `0` — динамическое условие
подключайте ко входу `condition` блока.

Пример: `data.number 5` → `action.setvar(name: "bonus", scope: "sheet")`, затем в этом же
действии `data.var(bonus) > 3` → `condition` блока `action.field`. Условие считается после
`setvar` по обновлённым переменным, а `sheet.vars.bonus = 5` остаётся на листе.

### Ссылка на узел

`data.ref` — выход `value: number`, входов нет; параметр `node` — ID другого узла **этого
же графа** (внутри повторно используемой группы — узла этой группы). Значение ссылки —
значение цели в том же контексте выполнения, поэтому ссылка видит и лист, и результаты, и
переменные.

- Цель обязана существовать и отдавать `value: number`; узлы границ группы
  (`group.input`/`group.output`), экземпляры групп и `flow.*` не подходят.
- Ссылка на себя отклоняется: «Ссылка: узел не может ссылаться на себя».
- Цепочка ссылок не должна замыкаться: `ref A → ref B → ref A` — ошибка «Циклическая
  ссылка» при сохранении. Испорченная запись с циклом не подвешивает сервер: вычисление
  значений ограничено по глубине и вложенности.
- Цель-`data.ref` разворачивается до первого нессылочного узла; цепочка собирается в том же
  графе, поэтому в развёрнутом графе группы ID получает префикс экземпляра.
- Предпросмотр в редакторе статический: ссылка на `data.number` показывает его число,
  ссылка на `data.var`/`data.sheet` — `0` (как и сами эти узлы без состояния выполнения).

### Математика

`data.mathfun` — выход `value: number`. Входы `a`, `b`, `c` — числа; таблица операций
одна на клиенте (`NodeRegistry.mathfunValue`) и на сервере (`mathfun_value`):

| `op` | Что делает | Нужные входы |
|---|---|---|
| `min` / `max` | минимум / максимум двух чисел | `a`, `b` |
| `clamp` | `min(max(a, b), c)` — загнать `a` в диапазон `b…c` | `a`, `b`, `c` |
| `abs` | модуль | `a` |
| `round` | округление половины вверх (`floor(a + 0.5)`) | `a` |
| `floor` / `ceil` | вниз / вверх | `a` |
| `sign` | `−1`, `0` или `1` | `a` |

- Неизвестная операция отклоняется при сохранении.
- `clamp` без проводов на `b` и `c` — смысловая проблема: запись сохраняется, но граф не
  исполняется («Математика: для clamp нужны провода на входы b и c»).
- Недостающий или нечисловой вход — неизвестное значение (`undefined` при компиляции и
  предпросмотре, `null` в рантайме); условие считается неизвестным и блок не пропускается.
- `round` считает половину вверх и для отрицательных чисел: `round(-2.5) = -2`.

### Строки и списки

Семь узлов категории «Данные» дают визуальному программированию текст и списки: строку можно
собрать, обрезать, измерить и сравнить, а список — задать литералом, прочитать по индексу и
склеить. Значения читаются из проводов, как у `data.mathfun`; на лист эти узлы ничего не
пишут, а в блоки плана попадает только вычисленный результат — число для `action.setvar`
или `condition_src` для условия блока: `bool` из `data.textcheck` (или `data.compare`
поверх `data.textlen`) идёт на вход `condition`, и сервер считает условие в рантайме.

| Узел | Что делает | Особенности |
|---|---|---|
| `data.text` | `concat` склеивает `a` и `b`, `upper`/`lower` меняют регистр, `trim` убирает пробелы по краям | `b` читает только `concat`; вход, к которому не подведён провод, считается пустой строкой |
| `data.textlen` | длина строки в символах Unicode (кодовых точках) | «𝄞» — один символ, хотя в UTF-16 занимает две единицы; без провода — `0` |
| `data.textcheck` | `contains`, `starts`, `ends`, `eq`, `ne` | `case: false` (по умолчанию) — без учёта регистра; `case: true` — регистр важен |
| `data.list` | литерал списка из параметра `items` | входов нет, значение доступно без состояния выполнения: до 100 строк по 200 символов |
| `data.listget` | элемент по индексу (с нуля) | дробный индекс усекается; индекс вне диапазона и пустой список дают пустую строку |
| `data.listlen` | число элементов списка | без провода или с пустым списком — `0` |
| `data.listjoin` | склейка списка через `separator` | разделитель до 10 символов, по умолчанию «, »; пустой список — пустая строка |

- Таблицы операций и сравнений одни на клиенте (`NodeRegistry.textValue` /
  `textCheckValue`) и на сервере (`text_value` / `text_check_value`); `TEXT_OPS` и
  `TEXT_CHECK_OPS` сверяет `node tools/srd/integrity.cjs`.
- Неизвестная операция, `items` не массив, строка списка длиннее 200 символов, больше
  100 элементов и разделитель длиннее 10 символов отклоняются при сохранении.
- Предпросмотр считает значения по литералам и проводам: `data.list` → `data.listjoin` →
  `data.textlen` → `action.setvar` показывает число без исполнения графа. Неизвестная
  операция даёт неизвестное значение (`undefined`); подключённый к нему узел считает по
  своим правилам — например, `data.textlen` вернёт `0`.

## Функции-группы

Группа повторного использования (`graph.groups`) может быть **функцией**: её границы
`group.input`/`group.output` описаны value-сокетами, а узел `data.call` вызывает её как
значение и возвращает типизированный результат.

- **Параметры.** В интерфейсе группы у каждого `group.input` есть `name` (пусто или 1–32
  символа `[a-z0-9_]`) и `type` = number/text/bool/list; по умолчанию number. У
  `group.output` — `type` результата. Для функции нужен **ровно один** выход и **не более
  трёх** входов; иначе узел вызова отклоняется.
- **Только значения.** В графе группы-функции допустимы `data.*`, `logic.op`,
  `dice.combine`, `condition.*` и границы группы. Действия, поток, правила и
  `group.instance` запрещены: `Группа-функция не может содержать блоки действий`.
  Вложенность выражается вторым `data.call`.
- **Вызов.** `data.call` имеет входы `a`, `b`, `c` (number) и выход `value` типа
  `result`. Аргументы привязываются к входам группы **по порядку** массива
  `group.inputs`, имена игнорируются; лишние `b`/`c` у группы с одним входом просто не
  используются. `result` обязан совпадать с типом выхода группы.
- **Вычисление.** Клиент (`groupValue` в `static/mechanics-graph.js`) и сервер
  (`call_group_value` в `src/mechanics_graph.rs`) находят группу, подставляют аргументы на
  `group.input`, считают значение, поданное на `group.output`, и приводят его к `result`.
  Без значения (неподключённый вход, отсутствующий runtime, неизвестное значение) —
  `0` / `""` / `false` / пустой список.
- **Защита.** Рекурсия `A → B → A` отклоняется при сохранении сообщением
  `Рекурсивный вызов группы`; при вычислении дополнительно ограничена глубина 16
  вызовов. Циклы с участием `group.instance` ловит общий запрет циклов между группами.

Пример: группа `g-add` с входами `x`, `y` и выходом `number` содержит
`group.input(x) → data.math(add) ← group.input(y)`, а `data.math.value` идёт на
`group.output`. Узел `data.call { group: "g-add", result: "number" }` с проводами
`2 → a`, `3 → b` даёт `5`. Вложенная группа вызывает `data.call` вместо `group.instance`.

## Заклинания

Каст — программа `action.program` → `action.slot` → броски и правила. `action.slot.level = 0`
означает «круг выбирает игрок»: клиент перед кастом показывает круги от базового до 9-го,
в которых есть свободные ячейки, и отправляет `slot_level` в операции `program`. Сервер
проверяет `base ≤ chosen ≤ 9`, списывает ячейку нужного круга (обычную, иначе ячейку
Договора) и кладёт `{ level, base, extra }` в контекст выполнения:

- `extra = chosen - base`; у `action.roll` (damage/heal) с `upcast` к формуле добавляется
  `extra*count` костей `sides` — например, «Огненный шар» 3-го круга ячейкой 5-го бросает
  `8d6+2d6`;
- `data.cast` читает `level` / `base` / `extra` (без каста — 0);
- ритуал: `slot_level = 0` при `base > 0` разрешён только заклинанию со свойством «Ритуал»;
  блок `action.slot` пропускается, в ответе эффект «Ритуал: 10 минут, ячейка не тратится»;
- концентрация: после успешного каста сервер заменяет состояние «Концентрация: …» именем
  заклинания (прежняя запись удаляется, чужие состояния остаются);
- `action.field` status с `operation: concentration` — явный узел того же поведения для
  редактора; `condition` у него пустой, имя подставляет сервер.

Контекст каста живёт только на время выполнения (`sheet.cast` ставится перед блоками и
удаляется до нормализации), в листе сохраняются лишь ячейки, состояния и `action_results`.
Шаблон «Ячейка → лечение» использует `action.slot` с `level: 1`; SRD-заклинания —
`action.slot` с `level: 0`, `upcast` по тексту `higher_level` и узел концентрации.

Новые шаблоны (появились вместе с унификацией палитры):

| Шаблон | Цепочка |
|---|---|

## Редактор: подключение узлов из меню

ПКМ по узлу показывает над обычными пунктами две секции: **«Подключить к этой ноде»**
(выход нового узла совместим с любым входом текущего — новый узел подключается к текущему)
и **«Подключить от этой ноды»** (вход нового узла совместим с любым выходом текущего).
Совместимость считается по типам сокетов `NodeRegistry` с учётом `def.ports(params)`
(например, у `logic.op` с `op: not` нет входа `b`); сам тип, `group.*`, «Начало» и «Конец»
не предлагаются. В пункте жирным стоит `nodeTitle`, ниже — пара сокетов (`exec → exec`,
`value → condition`). Секция показывает до 9 типов по категориям палитры, а у блока
действия условия идут первыми. Клик создаёт узел рядом (+40 px, не поверх соседей) и
проводит провод к свободному входу (приоритет: exec→exec, flow/effect, затем по типу);
узел и провод отменяются одним Undo. Если свободного входа нет или `connectionError`
против, узел добавляется без провода, а статус объясняет причину. Например, `condition.hit`
по-прежнему допустим только ко входу «Если», поэтому из секции он добавляется без провода.
