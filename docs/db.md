# База данных: индексы, планы запросов и замеры

Документ про то, какие запросы к БД оптимизированы, какие индексы для этого добавлены и как
померять эффект самому. Поведение API при этом не менялось: те же строки, тот же порядок, те же
коды ошибок.

## Как устроено

- Доступ к БД — `sqlx::AnyPool` (`src/store/db.rs`): SQLite (локально, **пул = 1 соединение**, поэтому
  каждый лишний запрос — это ещё один последовательный обмен) или MySQL 8.4 (CI/прод).
- Схема и индексы описаны в одном месте — `src/store/db.rs`: `SCHEMA` (CREATE TABLE), `ALTERS`,
  `INDEXES`. `migrate()` гоняет их на каждом старте: `ALTER` и `CREATE INDEX` идемпотентны
  (`IF NOT EXISTS` для SQLite; для MySQL ошибка «индекс уже есть» / 1061 игнорируется).
- SQL пишется вручную и должен работать на обоих движках: `CREATE INDEX ... ON t(a, b)` — общий
  синтаксис, ключи короткие (`id` — `VARCHAR(32)`, время — `VARCHAR(40)`), самый длинный новый
  ключ `compendium(pack_id, category, name)` — 736 байт в utf8mb4 при пределе InnoDB 3072.

## Добавленные индексы

| Индекс | Обслуживает | Что даёт |
|---|---|---|
| `characters(campaign_id, updated_at)` | `GET /api/characters?campaign_id=…` | убирает `TEMP B-TREE` у `ORDER BY updated_at DESC` |
| `characters(owner_id, updated_at)` | `GET /api/characters` (свои листы) | то же для `ORDER BY updated_at DESC` |
| `scenes(campaign_id, created_at)` | `GET /api/campaigns/:cid/scenes` | то же для `ORDER BY created_at` |
| `scene_items(scene_id, z)` | `GET /api/campaigns/:cid/scenes/:sid` | то же для `ORDER BY z` (элементы стола) |
| `compendium(category, name)` | `GET /api/compendium?category=…` | сортировка берётся из индекса, без `TEMP B-TREE` |
| `compendium(pack_id, category, name)` | записи набора (`/api/packs/:id/export`, статистика по категориям) | без сортировки + покрывает `GROUP BY category` |
| `pack_editors(user_id)` | `GET /api/packs?scope=mine|all`, поиск по справочнику | было `SCAN pack_editors`, стало поиском по индексу |
| `campaign_packs(pack_id)` | `packs::can_read`, отключение набора | было `SCAN campaign_packs`, стало поиском по индексу |

Старые одиночные индексы (`idx_chars_campaign`, `idx_comp_pack`, `idx_comp_category`, …) оставлены:
на уже существующих базах они всё равно есть, а новые составные их перекрывают по префиксу.

## Изменённые запросы

1. **`GET /api/packs` (список наборов) — убран N+1.** Было: основной запрос + по два `COUNT(*)`
   на каждый набор (`subscribed`, `editor`) — при 179 наборах это **359 запросов** на один
   HTTP-запрос. Стало: два коррелированных подзапроса в списке колонок основного `SELECT` —
   **1 запрос**. Параметры этих подзапросов идут в SQL раньше условий `WHERE`, поэтому они
   биндятся первыми (см. комментарий в `packs::list`).
2. **`stats()` набора — 4 запроса → 2.** `subscribers`, `subscribed`, `editor` считаются одним
   запросом с тремя скалярными подзапросами; разбивка по категориям осталась отдельным `GROUP BY`.
3. **`packs::can_read` возвращает прочитанную строку набора.** `GET /api/packs/:id`, `…/export`,
   `…/clone` больше не делают повторный `SELECT` той же строки (было 3 чтения `packs` на запрос,
   стало 1–2).
4. **`GET /api/campaigns/:cid` — 3 запроса → 2.** Роль участника и кампания читаются одним
   `JOIN`; если строки нет — 403 «Вы не участник этой кампании» (как и раньше: сначала
   проверялся участник, потом кампания).
5. **`GET /api/campaigns/:cid/scenes/:sid` — 3 запроса → 2.** Сцена читается вместе с ролью
   участника (подзапрос). Разделение ошибок сохранено: не участник — 403, участник без сцены —
   404. Элементы сцены остаются отдельным запросом: `JOIN` размножил бы поля сцены на каждый
   элемент.

## Замеры (локально, SQLite)

Стенд: копия рабочей БД + синтетика — 500 персонажей в кампании (лист ~2 КБ), 1000 сообщений чата,
5 сцен по 200 элементов, 151 ассет (по 20 КБ `data_b64`), 202 набора, 3627 записей справочника.
Медиана 40–120 прогонов одного подготовленного запроса (`node:sqlite`, WAL, без `ANALYZE`).
Числа — с одной машины, разброс между прогонами ±5–10 %.

| Запрос | Было | Стало |
|---|---|---|
| персонажи кампании (500 строк) | 1.189 мс (+ сортировка) | **0.690 мс** |
| персонажи владельца (250) | 0.590 мс (+ сортировка) | **0.346 мс** |
| элементы сцены (200) | 0.183 мс (+ сортировка) | 0.173 мс |
| список сцен (5) | 0.011 мс (+ сортировка) | 0.010 мс |
| записи набора (25) | 0.037 мс (+ сортировка) | **0.028 мс** |
| список наборов (179) | 359 запросов, 1.44 мс | **1 запрос, 0.89 мс** |
| сводка набора | 4 запроса, 0.21 мс | **2 запроса, 0.11 мс** |
| доступ к набору (`can_read`) | 0.011 мс (`SCAN campaign_packs`) | 0.005 мс |
| кампания + роль | 2 запроса | 1 запрос |
| сцена + роль | 2 запроса | 1 запрос |
| чат, последние 100/500 | 0.22 / 1.02 мс | без изменений (см. ниже) |
| ассеты (список) | 0.91 мс | без изменений (см. ниже) |
| справочник: категория | 0.37 мс | 0.37 мс, но без `TEMP B-TREE` |
| справочник: поиск подстроки | 6.8 мс | без изменений (см. ниже) |

`EXPLAIN QUERY PLAN` до/после (характерное):

```
-- персонажи кампании, было
SEARCH characters USING INDEX idx_chars_campaign (campaign_id=?)
USE TEMP B-TREE FOR ORDER BY
-- стало
SEARCH characters USING INDEX idx_chars_campaign_updated (campaign_id=?)

-- записи набора, было
SEARCH compendium USING INDEX idx_comp_pack (pack_id=?)
USE TEMP B-TREE FOR ORDER BY
-- стало
SEARCH compendium USING INDEX idx_comp_pack_cat_name (pack_id=?)

-- чат (индекс не понадобился: id — PK/rowid, он и так есть в ключе вторичного индекса)
SEARCH m USING INDEX idx_chat_campaign (campaign_id=?)
SEARCH u USING INDEX sqlite_autoindex_users_1 (id=?)
```

## Как померить самому

1. Возьмите копию рабочей базы (не саму базу — стенд пишет в файл):

   ```bash
   cp data/dnd.db /tmp/bench.db          # SQLite; WAL-файлы можно не копировать
   ```

2. `EXPLAIN QUERY PLAN` и замер — обычным `node:sqlite` (Node.js 22+), без зависимостей:

   ```js
   const { DatabaseSync } = require('node:sqlite');
   const db = new DatabaseSync('/tmp/bench.db');
   const sql = 'SELECT * FROM characters WHERE campaign_id = ? ORDER BY updated_at DESC';
   console.log(db.prepare('EXPLAIN QUERY PLAN ' + sql).all('cid')); // ищем TEMP B-TREE / SCAN
   const st = db.prepare(sql);
   for (let i = 0; i < 20; i++) st.all('cid');                        // прогрев
   const t = [];
   for (let i = 0; i < 100; i++) { const s = performance.now(); st.all('cid'); t.push(performance.now() - s); }
   t.sort((a, b) => a - b); console.log('медиана, мс:', t[50]);
   ```

3. Что искать в плане: `SCAN <таблица>` (полный проход), `USE TEMP B-TREE FOR ORDER BY`
   (сортировка, которую можно снять индексом), `MULTI-INDEX OR` (дорогой `OR`), а в коде —
   `sqlx::query` внутри `for`/`map` (это N+1).

4. Для «до/после» на одной и той же базе: снять цифры, применить `INDEXES` из `src/store/db.rs`
   (`dnd-table stats` при `DATABASE_URL=sqlite://…` прогоняет `migrate()`), снять цифры снова.

Миграция проверена на базе, созданной предыдущей версией: 19 индексов → 27 после старта,
повторный старт оставляет 27 (повторный прогон идемпотентен, ошибок нет).

## Что осознанно не менялось

- **`chat_messages(campaign_id, id)`** не нужен: `id` — целочисленный первичный ключ (rowid в
  SQLite, PK в InnoDB), и он уже входит в ключ вторичного индекса `idx_chat_campaign`. Поэтому
  `WHERE campaign_id = ? ORDER BY id DESC LIMIT ?` идёт по индексу без сортировки — в плане нет
  `TEMP B-TREE`, пагинация не тянет всю историю.
- **`campaign_members(user_id, campaign_id)`** не нужен: обратный поиск уже покрыт
  `idx_members_user(user_id)`, проверка участия — `UNIQUE(campaign_id, user_id)`, а роль всё равно
  требует чтения строки таблицы, так что покрывающий индекс ничего не экономит.
- **Список ассетов** (`GET /api/assets`): `builtin = 1 OR owner_id = ? OR campaign_id = ?` — три
  источника, поэтому SQLite делает `SCAN assets` и сортирует. Строки широкие (`data_b64`), но
  незапрошенные overflow-страницы SQLite не читает. Покрывающий индекс по всем полям метаданных
  помог бы только SQLite (в MySQL `OR` всё равно не даст его использовать) и сильно удорожил бы
  вставки ассетов — не добавляли.
- **Поиск по справочнику подстрокой** (`q=…` → `name_lc LIKE '%…%'`): индекс для `%…%` не
  работает; план — `MULTI-INDEX OR` + фильтр по `LIKE`, ~6.8 мс на 3.6 тыс. записей (полный проход
  по таблице дал бы ~6 мс — выигрыш в пределах шума, а переписывание `OR` в `UNION` меняет
  семантику сортировки/дублей). Быстрое решение — FTS5 в SQLite против `FULLTEXT` в MySQL —
  это новая схема и разное поведение движков, отдельная задача.
- **`GROUP BY`/`COUNT` в админ-командах** (`users show`, `stats`) — CLI/админ-эндпоинт, не горячий
  путь; лишние запросы там дешевле, чем риск в отформатированном выводе.
- **Кэш справочника не вводили.** Выборка `/api/compendium` зависит от прав: базовые записи +
  homebrew кампании + подключённые к ней наборы + свои наборы/подписки/соавторство. Кэш без ключа
  «пользователь × кампания × набор» отдал бы чужие записи, а с таким ключом почти не экономит
  (промах на каждое изменение набора). Настройки и так живут в памяти (`Config` в `AppState`).
- **Presence и эфемерные события стола** (`pointer`, `ping`, `cursor`, `ruler`, `initiative`) в БД
  не пишутся вообще — они живут в памяти хаба (`src/ws/realtime.rs`). В БД попадают только реальные
  изменения (элемент, сцена, сообщение чата).
