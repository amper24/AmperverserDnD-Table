# Профиль пользователя (`/profile`)

Отдельная страница изменения профиля: имя, аватар, почта, пароль и управление
аккаунтом. Страница не входит в SPA `static/app.js` (там остался старый диалог
профиля для совместимости) и открывается по прямому маршруту `/profile`.

## Файлы

| Файл | Назначение |
|---|---|
| `static/profile.html` | Разметка страницы: шапка, блоки «Основное», «Почта», «Пароль», «Аккаунт». |
| `static/profile-page.js` | Вся логика страницы: загрузка `/api/auth/me`, dirty-индикатор, аватар, коды почты, пароль, удаление. |
| `static/profile-page.css` | Оформление только этой страницы; цвета — из переменных `style.css`, поэтому тёмная и светлая темы работают без дублирования. |
| `src/api/auth.rs` | Эндпоинты профиля, валидация имени/почты/пароля, сессии, удаление аккаунта, unit-тесты. |
| `src/main.rs` | Один маршрут: `GET /profile` → встроенный `profile.html`. |
| `tests/profile-page.browser.cjs` | Браузерный тест страницы на моках HTTP API. |
| `scripts/smoke.sh` | Шаги `[10]` и `[10b]`: профиль, сессии, почта, пароль. |

## Поля пользователя

`users`: `id`, `email` (уникальный, хранится в нижнем регистре), `name`,
`password_hash` (argon2, может быть `NULL`), `verified`, `is_root`,
`avatar_asset_id` (ссылка на `assets.id`), `created_at`, `google_sub`.

Аватар — обычный ассет: либо загруженный пользователем
(`assets.owner_id = users.id`), либо встроенный (`assets.builtin = 1`). Страница
загружает и предлагает портреты (`kind = 'portrait'`), но сервер, как и раньше,
принимает любой свой ассет или встроенный — так старые аватары-токены продолжают
работать. Чужой пользовательский ассет поставить аватаром нельзя.

## Эндпоинты

Все эндпоинты ниже работают только с пользователем из текущей сессии
(`AuthUser`: cookie `dnd_session` / `dnd_session_x` или `Authorization: Bearer`).
Параметра «id пользователя» у них нет, поэтому root не может изменить чужой
профиль этим API — для чужих аккаунтов остаётся только `/api/admin/users/:uid`.

### `GET /api/auth/me`

Возвращает `id`, `email`, `name`, `is_root`, `avatar_asset_id`, `created_at`,
`has_password`. `has_password` нужен странице, чтобы не спрашивать текущий
пароль у аккаунта, созданного по коду и ещё не задавшего пароль.

### `PATCH /api/auth/me`

Тело: `{ "name"?: string, "avatar_asset_id"?: string | null }`.

* `name` обрезается по краям и обязан быть длиной 1..64 символа (в символах
  Unicode, не в байтах). Длинное имя отклоняется с `400`, а не обрезается молча.
* `avatar_asset_id` — `null` убирает аватар; иначе ассет должен существовать и
  быть своим (`owner_id = пользователь`) или встроенным (`builtin = 1`).
* Ответ: `{ "ok": true, "name": ..., "avatar_asset_id": ... }`.
* Пустой PATCH допустим и просто возвращает текущие значения.

### `POST /api/auth/change-email/request-code`

Тело: `{ "email": "new@example.com" }`.

1. Адрес нормализуется (`trim` + нижний регистр) и проверяется тем же правилом,
   что регистрация и вход (`check_email`).
2. Отклоняется, если это текущая почта или адрес уже занят другим аккаунтом.
3. Выпускает 6-значный код в `auth_codes` и отправляет его на новый адрес
   (`smtp.*` в `config.yml`). Без SMTP код печатается в консоль сервера, а при
   `auth.dev_show_code: true` возвращается в `dev_code` (только для разработки).

Ответ: `{ "ok": true, "sent": bool, "ttl_min": n, "email": ..., "dev_code"?: ... }`.

### `POST /api/auth/change-email`

Тело: `{ "email": "new@example.com", "code": "123456", "password"?: "..." }`.

* Код обязателен, проверяется существующим `consume_code`: TTL, число попыток,
  одноразовость — те же, что при входе и сбросе пароля.
* Если у аккаунта уже есть пароль, требуется текущий пароль (проверка argon2).
  Это не даёт украденной сессии сменить почту и затем сбросить пароль.
* Уникальность проверяется до выпуска кода и повторно после проверки кода; гонка
  на уникальном индексе `users.email` превращается в понятную ошибку `400`.
* Успех: `UPDATE users SET email = ?, verified = 1`, старые неиспользованные коды
  на прежний адрес помечаются использованными. Ответ: `{ "ok": true, "email": ... }`.

### `POST /api/auth/change-password`

Тело: `{ "old_password": "...", "password": "..." }`.

* Новый пароль проверяется `auth.password_min_length` из `config.yml` (8 по
  умолчанию, максимум 200 символов).
* Если пароль уже задан, старый проверяется argon2; иначе пароль можно задать
  без старого (аккаунт, созданный по коду).
* После успеха все сессии пользователя, кроме текущей (токен из cookie/Bearer),
  удаляются из `sessions`.

### `POST /api/auth/logout-all`

Удаляет **все** сессии пользователя, включая текущую, и очищает обе cookie.
Страница после этого очищает `dnd_token` и уходит на `/`.

### `DELETE /api/auth/me`

Тело: `{ "email": "текущая@почта" }`.

* Почта должна совпадать с текущей (нормализованное сравнение) — это защита от
  случайного удаления.
* Последнего root удалить нельзя: сервер отвечает `400`.
* Удаление выполняет `admin::delete_by_id`: явно удаляются кампании владельца
  (вместе со сценами, элементами сцен, приглашениями, чатом и ассетами
  кампаний), затем персонажи владельца, его наборы, ассеты, членства, подписки,
  соавторство и сессии. Персонажи других игроков в удалённых кампаниях остаются,
  но теряют привязку к кампании (`campaign_id` → `NULL`). Сама запись `users`
  удаляется последней.
* Cookie сессии очищаются в ответе.

## Сессии и безопасность

* `sessions(token PK, user_id, created_at)`; `user_id` — внешний ключ на
  `users(id) ON DELETE CASCADE`. Срок жизни — `auth.session_days` (0 — без
  ограничения), проверяется в `user_by_token`.
* Смена пароля и «выйти на всех устройствах» работают с этой таблицей; отдельной
  таблицы «устройств» нет.
* Пароли — argon2id (по умолчанию `argon2` crate), коды — 6 цифр, TTL и лимит
  попыток из конфигурации.
* Почта — логин: после смены старый адрес перестаёт логинить, новый работает
  сразу (пароль и сессии не меняются).
* CSRF: как и во всём API, отдельного CSRF-токена нет. Защита — HttpOnly
  SameSite=Lax cookie (плюс `SameSite=None; Secure; Partitioned` для фрейма) и
  требование JSON-тела: межсайтовый POST с `application/json` требует preflight.
  Это осознанное ограничение текущего API, а не «защита на словах»; при
  необходимости CSRF-токены можно добавить отдельной задачей.
* root не может править чужой профиль через эти эндпоинты: обработчики не
  принимают id и берут пользователя только из сессии.

## Аватар: загрузка и библиотека

1. **Файл** — `POST /api/assets` (multipart, `file`, `kind=portrait`, `name`);
   сервер сжимает изображение (`images.*`), кладёт в `assets` и возвращает `id`.
2. **Библиотека** — `GET /api/assets?kind=portrait`; в модальном окне показываются
   портреты пользователя и встроенные. Выбор только подставляет `id` в черновик.
3. `PATCH /api/auth/me { avatar_asset_id }` сохраняет выбор. До нажатия
   «Сохранить» страница показывает черновик и dirty-индикатор; «Отмена»
   возвращает сохранённое значение. Загруженный, но не сохранённый ассет остаётся
   в библиотеке — это нормально и не является «мусором» (его можно выбрать позже).

## Клиентская валидация

Страница повторяет серверные правила, чтобы ошибка была видна сразу:

* имя — 1..64 символа после `trim`, пустое/длинное блокируется до запроса;
* почта — регулярное выражение вида `name@domain.tld`, совпадение с текущей и
  занятые адреса объясняются отдельно;
* пароль — минимум `password_min_length`, повтор должен совпадать, при заданном
  пароле старый обязателен;
* удаление — кнопка активна только после ввода текущей почты.

Серверные ошибки показываются в `role="alert"` рядом с соответствующим блоком;
успехи — тостами. Все поля связаны с `label` через `for`, у кнопок и полей есть
понятные подписи, dirty-индикатор и сообщения кода — `aria-live="polite"`.


## Ограничения

* Коды почты без SMTP видны только в консоли сервера (и в `dev_code` при
  `dev_show_code: true`); это режим разработки, в продакшене нужен SMTP.
* Отдельного rate-limit на `request-code` нет; ограничение — TTL и число попыток
  ввода кода (`auth.code_ttl_minutes`, `auth.code_max_attempts`).
* При удалении аккаунта сообщения чата, отправленные пользователем в чужих
  кампаниях, остаются (у `chat_messages.user_id` нет внешнего ключа на `users`);
  строки `auth_codes` также не удаляются. Это не влияет на вход и данные профиля,
  но при требованиях полного стирания нужна отдельная очистка.
* `avatar_asset_id` не имеет внешнего ключа (как и в исходной схеме); удаление
  ассета из библиотеки не обнуляет аватар автоматически. Пользователь может
  выбрать новый аватар на этой странице.
* Аватар — только изображение; видео и произвольные файлы не поддерживаются.
