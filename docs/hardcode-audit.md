## Формулы и ассеты — что сделано

- **Формулы.** Новый модуль `static/formulas.js`: безопасный вычислитель (без `eval`), грамматика `+ − * /`, скобки, `min`/`max`, переменные `@name`. Переменные описаны реестром `VARIABLES` (модификатор характеристики или поле листа). Добавить переменную — одна строка данных.
- **Защита без доспехов.** Правило хранится в записи класса: пассивный блок `unarmored_defense` с `formula`, `no_shield` (необязательно `name`). Варвар и монах обеих редакций уже имеют его в `data_seed`. Классы без правила получают обычную КД. Сервер принимает новое поле (`src/mechanics.rs`), узел графа `rule.armor_formula` проверяется тем же грамматическим правилом (`src/mechanics_graph.rs`, `static/mechanics-graph.js`).
- **Переходный слой.** Старые листы с `unarmored_defense: 'barbarian'`/`'monk'` читаются через `Formulas.legacyUnarmored(slug)` (поле `legacy_unarmored` набора `class_rules`). Это единственное оставшееся упоминание классов в расчёте КД; новые записи его не используют.
- **Ассеты.** Типы (карта, токен, объект, портрет, предмет) описаны одним реестром `static/asset-kinds.js` (подписи, списки выбора, слой на столе, квадратная раскладка). Серверный список — константа `ASSET_KINDS` в `src/assets.rs`. Тест `tests/asset-kinds.test.cjs` сверяет оба списка и не даёт вернуть литералы в `app.js`/`table.js`.
- **Ограничение данных.** Механики в записях, уже сохранённых в базе, не обновляются сидом (правило сохраняет пользовательские правки). В новых установках правило уже есть; в существующей базе его можно добавить в редакторе записи, пассивным блоком `unarmored_defense`.

## Итерация «по порядку»: что перенесено

- **Лимиты размеров картинок.** `src/config.rs`: `KIND_SIZE_CLASS` — тип ассета → класс лимита (карта или токен). `max_side(kind)` больше не сравнивает строку `"map"`; тест сверяет таблицу со списком `ASSET_KINDS`. Значения в `config.yml` и переменные окружения прежние. Примечание: Rust в этой среде не собирается (нет cargo), тесты Rust нужно прогнать в CI.
- **Переменные модулей.** `static/modules.js`: производные переменные (`@best`, `@atk`, `@atk_str`, `@atk_dex`, `@spell`, `@dc`, `@spell_dc`, `@init`) — строки таблицы `DERIVED_VARS` с формулами. `Formulas.evaluate` принимает набор допустимых имён (`allowed`), по умолчанию переменные листа. Снимок значений до и после переноса совпадает.
- **Прогрессия класса из узла.** `Mechanics.classProgression(mechanics, edition)` читает таблицу из узла `rule.class_progression` в записи класса; условие редакции (`condition.edition`) выбирает таблицу. Порядок чтения: данные записи → граф → набор `class_progression` (запасной вариант для SRD). Используется в `levelup.js` и `character-builder.js` (лимиты заклинаний 1 уровня).

- **Правила классов — узлы и наборы.** Кастеры, требования и владения мультикласса, мастерства оружия, цвет класса и русские имена берутся из узла `rule.class_rules` записи класса (`Mechanics.classRules(mechanics, edition)`), запас — набор `class_rules` по slug и редакции. Таблицы `SRD_CASTER`, `MC_REQ`, `MC_PROF`, `CLASS_COLOR`, `LEGACY_UNARMORED` и словарь мастерств удалены из кода. Миграция: `node tools/srd/add_class_progression_nodes.cjs` (второй узел). Тест: `tests/class-rules-node.test.cjs`.
- Старые записи (блок `data.caster`) по-прежнему читаются первыми — для совместимости.

  - списки заклинаний-алиасов в `builder-dialog.js` ~266–299 (`'жрец'`, `'cleric'` и т. д.).
- Монах: фильтр оружия (`character-builder.js` ~545) и тексты предысторий-классов остаются литералами.
- `static/mechanics.js`: умолчания блоков атаки/урона (`1d20+@atk`, `1d6`) и состояния (`Отравленный`, `Испуганный`) зашиты в конструкторе блоков; нужно перенести в реестр узлов.
- **Таблицы развития SRD — узлами.** Каждый класс SRD 2014/2024 в `data_seed` несёт узел `rule.class_progression` с таблицей (перенос: `node tools/srd/add_class_progression_nodes.cjs`, идемпотентно; тест `tests/class-progression-seed.test.cjs`). Английский вид — оверлей узла с подписями колонок.

Пользователь добавляет свой набор через диалог «Наборы данных…» или файлом в репозиторий (`docs/presets.md`). `class-progression.js` и `presets-data.js` удалены.
- Браузерные тесты запускаются в CI (job `browser`): dice, forms-create, mechanics-graph, mechanics, node-card, node-editor, presets-manager. `equipment.browser.cjs` не включён — падает и на main.

## Что остаётся

- **Таблицы классов в коде, не переведённые в наборы:** `levelup.js` (`SLUG_RU`); `class-rules.js` оставляет объект `RU_NAMES`, который заполняется из набора при загрузке (ссылка одна, потому что `builder-dialog.js` берёт её при загрузке скрипта). `builder-dialog.js` не трогается без отдельного запроса.
- **Старые строки SRD в базе** с правками не получают узел `rule.class_progression` (нужна миграция с legacy-хешами в `seed.rs`); им работает набор `class_progression`. Так же для узла `rule.class_rules`.

Перенос правил из таблицы выше — это отдельные этапы, каждый из которых меняет поведение мастера персонажа и повышения уровня. Порядок по риску: (1) формула КД варвара/монаха; (2) расы 2014/2024 с выбором навыков и языков; (3) заклинания по классам; (4) боевые стили, ордены, подклассы; (5) карта имён классов и таблицы прогрессии. Каждый этап сопровождается сверкой с `docs/node-rules-baseline/` и существующими JS-тестами.
