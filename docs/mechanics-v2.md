# Узловая схема механик v2

## Хранение

`data.mechanics` имеет закрытую, версионированную JSON-схему. Скрипты, формулы JS, `eval`, произвольные выражения, рекурсия графа и циклы запрещены.

```json
{
  "version": 2,
  "origin": "srd-graph-v2",
  "graph": {
    "nodes": [
      { "id": "n1", "type": "data.number", "params": { "value": 30 }, "position": { "x": 80, "y": 90 } },
      { "id": "n2", "type": "rule.speed", "params": {}, "position": { "x": 360, "y": 90 } }
    ],
    "links": [
      { "from": { "node": "n1", "socket": "value" }, "to": { "node": "n2", "socket": "value" } }
    ],
    "frames": [{ "id": "f1", "title": "Передвижение", "nodes": ["n1", "n2"] }],
    "groups": []
  }
}
```

`position` — только визуальная раскладка. Сохранённая запись не содержит выбора узла, zoom/pan или undo-истории. История undo/redo — локальные снимки редактора до нажатия «Сохранить».

## Узлы, порты и связи

Имена типов/портов — закрытые таблицы ядра, не расширяемые пользователем. Сервер и клиент применяют одинаковые ограничения и одинаковый алгоритм проверки.

- **Данные:** `data.number`, `data.dice`, `data.table`, `data.text`. Характеристику, навык и её производные (`@str`, `@str_score`, `@stealth`) задаёт один узел `data.stat` с режимом «бонус / значение»: значения характеристики в узле «Кость» нет, потому что показатель характеристики и её модификатор — не одно и то же, а дублировать список характеристик вторым узлом незачем.
- **Характеристики и навыки:** `data.stat` (выход `value: dice`) — параметры `id` (характеристика `str`…`cha` или навык из набора SKILLS) и `mode`: `bonus` — модификатор (для навыка уже с владением), `score` — значение характеристики или пассивное 10 + бонус для навыка. Значение — формула для броска (`@dex`, `@str_score`, `10+@acrobatics`), её считает лист при броске.
- **Сложение костей:** `dice.combine` (входы `a`, `b`: dice; выход `value: dice`) — одна формула `a + b`.
- **Кость в действии:** у настраиваемого узла «Бросок» (`action.roll`) есть вход `dice`. Провод на него заменяет поле `dice` блока.
- **Контекст/условия:** `condition.edition`, `condition.level`, `condition.subclass`, `condition.choice`; выход `value: bool`.
- **Сравнение:** `condition.compare` — входы `a`, `b: number`, параметр `op` (`>=`, `<=`, `>`, `<`, `=`, `!=`); выход `value: bool`. Пока сравниваются известные числа (узлы «Число» и вычисленные значения); значения характеристик персонажа в условиях графа не известны.
- **Логика:** один настраиваемый узел `logic.op` (входы `a`, `b: bool`; выход `value: bool`), операция `op` = `and` / `or` / `not` (для `not` используется только вход `a`). Неизвестное значение остаётся неизвестным, и обе ветви «Если» сохраняются. Вход «Попадание атаки» (`condition.hit`) к логике не подключается, только ко входу «Если». Старые типы `logic.and` / `logic.or` / `logic.not` — псевдонимы и переводятся редактором в `logic.op`.
- **Конец:** `flow.end` принимает несколько проводов (в конец могут прийти несколько узлов). В одном действии редактор не даёт добавить второй «Конец». Остальные входы принимают один провод.
- **Поток управления:** `flow.if`: вход `exec: flow` и `condition: bool`, выходы `then` / `else: flow`. Переводчик для исполнения выбирает ветку по контексту редакции, уровня, подкласса и `choices`; проверка без контекста сохраняет обе ветви.
- **Правила персонажа:** `rule.ability_bonus`, `rule.speed`, `rule.languages`, `rule.proficiencies`, `rule.hit_die`, `rule.saving_throws`, `rule.feature`, `rule.skills`, `rule.spell_list`, `rule.spell_slots`, `rule.asi`, `rule.class_progression`, `rule.armor_formula` (защита без доспехов: `formula`, необязательные `name` и `no_shield`), `rule.hp_bonus`, `rule.manual`, `rule.equipment` (фиксированный список стартового снаряжения: `items: [{name, qty}]`), `rule.equipment_choice` (выбор варианта снаряжения: `id`, `title`, `options: [{name, items, gold}]`). Формула — выражение из `static/formulas.js`: числа, `+ − * /`, скобки, `min`/`max`, переменные `@name` из реестра `VARIABLES`.

## Узлы — классы

Каждый узел — объектно-ориентированный класс в `static/nodes/<категория>/<файл>.js`: папка — категория (data / conditions / logic / flow / rules / actions / groups), файл — один узел. Класс наследует `GraphNode` (база в `static/node-registry.js`), объявляет метаданные (`type`, `label`, `group`, `inputs`, `outputs`, `defaults`) и своё поведение (`validate(params)`, `compute(params, get)` для вычисляемых, `project(params, env)` для правил) и регистрирует себя через `Nodes.register`. Движок `static/mechanics-graph.js` делегирует проверку/вычисление/проекцию классу узла, оставляя себе только ядро графа (топология, связи, канвас, компиляция действий в v1). Добавить узел = создать один файл-класс и подключить его тегом `<script>` в `static/index.html` и `static/sheet.html`.
- **Действия:** `action.program`, `action.consume`, `action.roll`, `action.grant_item`, `action.condition`, `action.adjust`, `action.require`, `action.manual`, `action.passive`. Все броски — один настраиваемый узел `action.roll`: параметр `roll_kind` (`roll` / `attack` / `damage` / `heal` / `temp_hp`) задаёт вид блока v1 при компиляции; старые типы `action.attack` / `action.damage` / `action.heal` / `action.temp_hp` — псевдонимы и переводятся редактором в `action.roll`. `action.*` сохраняет поля текущих блоков; ручное правило остаётся видимым и требует подтверждения по существующим правилам безопасности.
- **Повторное использование:** `group.instance` с сокетами, объявленными в интерфейсе группы; внутри группы интерфейс задаётся узлами `group.input` (выход `value`) и `group.output` (вход `value`). Типы портов границы должны совпадать с описанием интерфейса. Группы можно вкладывать; ссылки групп образуют отдельный ациклический граф, рекурсивные вызовы запрещены. При компиляции границы разворачиваются без сохранения исполняемого кода.

Каждый тип задаёт `inputs` / `outputs` и тип каждого сокета: `flow`, `bool`, `number`, `dice`, `text`, `table`, `effect` (в ядре зарезервированы ещё `ability`, `list`, `choice` — под сокеты интерфейса групп). Связать сокеты разных типов нельзя. У входного сокета одна связь; выход допускает веер. Для правила `enabled` необязателен: если он подключён, он должен быть `bool`. Условие передаётся по `enabled`, а не исполняемым кодом.

**Вход узла всегда можно подключить.** Порт, который не производит ни один узел, — ошибка системы: список навыков, заклинаний или языков задаётся параметром правила, а не висячим входом. Обратное тоже верно: выход, который никуда не подключается (кроме `effect` — конечного результата правила), в палитре не нужен. Это проверяют `tests/node-sockets.test.cjs` и `node tools/srd/integrity.cjs`: форма карточки узла, проверка умолчаний, работа проекции и паритет портов с сервером.

Ацикличность проверяется по всем связям узлов. Ограничены размер JSON, число узлов/связей/групп/рамок, размер ID/подписей, координаты, параметры узла и глубина вложенных групп.

## Редактор: холст и связи

- Реестр узлов — `static/node-registry.js` (`NodeRegistry`); движок связей — `Mechanics.connectionError` (тип, петля, цикл, `validateGraph`, с учётом уже существующих незавершённых мест).
- Меню добавления — `static/node-menu.js`, открывается ПКМ по полотну; категории задаются в `NodeRegistry.CATEGORIES`.
- Вид (зум, панорама) не сохраняется; в схему попадают только узлы, связи, позиции, рамки и группы.
- **Параметры на карточке.** Число, выбор, текст, кость и характеристика редактируются прямо на карточке узла (`static/node-params-form.js`, режим `valueEditor`). Поля останавливают распространение pointer-событий: ввод не двигает узел и не рвёт провода. Боковая панель остаётся для деталей и ошибок.

## Действия и ветки

- **Одно действие — один `action.program`.** Кнопка на листе запускает всю цепочку целиком через `evaluateGraph`; критичные эффекты (расход, урон, состояния) исполняются на сервере.
- **Ветки — через exec-связи.** Бросок атаки → `condition.hit` (попал/не попал) → `flow.if` → урон. Условия (попадание, уровень, ресурс) — только узлами условий, не полями блоков.
- **Гейт попадания.** `v2ToV1` переносит `when` в блоки v1: блоки под ветвями `then`/`else` получают `when: 'hit'`/`'miss'`. Стартовые графы «Атака» и «Урон» — отдельные действия со своими стилями (`attack`, `damage`). Ветка «атака → урон при попадании» в одном действии собирается вручную; такая цепочка показывается одной кнопкой программы (`.act-btn.all`).
- Шаблоны стартовых графов, предметов и заклинаний — наборы данных, см. `docs/presets.md`.

## Группы и рамки

Рамка — только визуальная группа ID узлов внутри графа. Один узел не может одновременно состоять в двух рамках; рамка не меняет порядок вычисления.

Группа повторного использования хранит `id`, `name`, типизированные `inputs`/`outputs`, `nodes` и `links`. Вызов `group.instance.params.group_id` должен ссылаться на существующую группу; типы его сокетов должны совпадать с интерфейсом. Каждому сокету интерфейса соответствует ровно один узел границы с тем же `socket_id`. Нельзя вызвать группу из самой себя ни напрямую, ни через другие группы.

## Данные персонажа

`rule.*` не содержат ссылок на конкретное имя расы/класса. Целевой формат стандартных записей хранит базовые параметры, эффекты, условия редакций/уровней/выборов, таблицы развития, spellcasting, подрасы/подклассы и choices в самой записи и подключённых группах. Сложное неструктурированное правило задаётся `rule.manual` с текстом и меткой «Применяется вручную».

Предпросмотр — чистая проекция выбранной редакции, уровня и текущих выборов на копию листа; API сохранения не вызывается. Вводы уровня и выбора не мутируют исходную запись.

## Совместимость со старой схемой

Старая схема `version: 1` (`programs[].blocks[]`) не поддерживается ни на клиенте, ни на сервере: `validate` принимает только граф v2, запись без механик открывается пустым графом, узлы старых типов (`action.attack`, `logic.and`, …) не существуют. Внутренняя проекция графа в плоский план (`toLegacy` на клиенте, `to_v1` на сервере) — это способ исполнения, а не чтение старых данных.

Seed-справочник полностью на v2: у записей классов есть узлы `rule.*` (прогрессия, правила класса, умения по уровням), у предметов, заклинаний и умений — графы программ. Открытая часть переноса — убрать ветвления по slug из мастера персонажа и повышения уровня; она не связана с форматом данных.
